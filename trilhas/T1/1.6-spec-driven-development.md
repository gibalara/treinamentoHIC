## Por quê

Na T2, o Claude Code constrói seu produto. Ele só acerta o que estiver escrito.

Spec-Driven Development é construir a partir de uma especificação escrita antes do código. O `SPEC.md` é esse arquivo: 8 seções que reúnem tudo o que você validou.

Ele fica no repositório e é atualizado a cada decisão. O marco da T1 exige as 8 seções completas.

## Demonstração

Exemplo: uma consultora sênior de RH que atende pequenas empresas. Produto: prepara a conversa de feedback a partir das anotações do gestor. Os documentos da validação estão em `projeto-hic/docs`.

1. Abra a pasta `projeto-hic` no modo de código do Claude Desktop (Claude Code), em **Manual**. [VERIFICAR NA INTERFACE]
2. Peça: "Inicie um repositório git nesta pasta." Repositório é a pasta cujas versões o git guarda.
3. Ative a skill de especificação do curso (pacote de instruções que o Claude segue). [LACUNA: nome, forma de entrega e instalação da skill de especificação não definidos na ementa] [VERIFICAR NA INTERFACE]
4. Peça: "Use a skill de especificação para gerar o SPEC.md de 8 seções a partir de docs."
5. Confira as seções 1 a 4 contra os arquivos de origem (veja "De onde vem cada seção", na Referência).
6. Responda às perguntas da skill para as seções 5 a 7: dados, IA no produto, regras.
7. Seção 6: tarefa de IA é rascunhar o roteiro de feedback; RAG usa os guias de avaliação da consultora.
8. Seção 5: avaliações são dados pessoais; o MVP (primeira versão usável) usa só dados fictícios.
9. Na seção 8, registre a decisão da síntese, com data e motivo.
10. Peça: "Faça um commit com a mensagem 'Adiciona SPEC.md v1'." Commit é uma versão salva.
11. Crie um repositório privado no GitHub e peça para enviar o commit. [VERIFICAR NA INTERFACE]

## Referência

**Template do `SPEC.md`**

```markdown
# [Nome do projeto]

## 1. Problema
- Dor:
- Quem sofre:
- Frequência:
- Alternativa atual e por que é insuficiente:

## 2. Usuários e papéis
- Usuário principal:
- Outros papéis (gestor, admin):

## 3. Proposta de valor
- Em uma frase:
- Métrica principal de sucesso:

## 4. Escopo do MVP
- Funcionalidades (com critérios de aceite):
- Fora do escopo (ver BACKLOG.md):

## 5. Dados
- Quais dados o produto usa:
- Origem dos dados:
- Dados sensíveis e tratamento:

## 6. IA no produto
- Tarefa de IA:
- Base de conhecimento (RAG):
- Ação candidata a agente (com aprovação humana):

## 7. Regras e restrições
- Regras de negócio:
- Restrições técnicas e de segurança:

## 8. Decisões tomadas
- [data] decisão + motivo
```

**De onde vem cada seção**

| Seção | Origem |
| --- | --- |
| 1. Problema | `docs/ficha-problema.md` + `docs/alternativas.md` |
| 2. Usuários e papéis | `docs/requisitos.md` |
| 3. Proposta de valor | `docs/proposta-e-metrica.md` |
| 4. Escopo do MVP | `docs/requisitos.md` (essenciais); "depois" vai para o `BACKLOG.md` (lição 1.7) |
| 5 a 7 | Perguntas da skill |
| 8. Decisões | `docs/decisao.md` + decisões das lições seguintes |

**Pedidos ao Claude Code**

- "Use a skill de especificação para gerar o SPEC.md a partir dos arquivos de docs."
- "Compare a seção [n] do SPEC.md com [arquivo] e aponte divergências."
- "Faça um commit com a mensagem 'Adiciona SPEC.md v1'."
- "Envie os commits para o GitHub."

**Termos**

- Spec-Driven Development: construir a partir de especificação escrita antes do código
- `SPEC.md`: arquivo de especificação do produto, em Markdown (texto simples com marcações)
- MVP: primeira versão usável, com o mínimo que resolve a dor
- RAG: a IA responde com base nos seus documentos, com citação (T4)
- Agente: IA que executa uma ação sozinha; no curso, sempre com aprovação humana (T6)
- Repositório: pasta cujas versões o git guarda
- Commit: versão salva da pasta

**Regras**

- Dados sensíveis reais não entram no MVP; use dados fictícios
- Chave de API (senha de acesso à IA) só no servidor, nunca no código: registre na seção 7
- Mudou uma decisão: atualize o `SPEC.md` e registre na seção 8
- Repositório fora do OneDrive (erro de `index.lock`, lição 0.5 da T0)
