# 1.5 · Funcionalidades com critério de pronto testável (requisitos e critérios de aceite)

- **Trilha:** T1 · Arquiteto de Produto
- **Tempo:** 60 min
- **Evidência:** requisitos
- **Status:** rascunho, ainda não cursado pelo aluno zero

## Por quê

O Claude Code constrói o que você pede, não o que você quis dizer. Requisito vago gera funcionalidade que parece pronta e não resolve.

Critério de aceite é a condição verificável que diz se a funcionalidade está pronta. Na T2, ele vira teste automatizado.

Sem critérios testáveis, o marco da T1 não é aprovado.

## Demonstração

Exemplo: uma consultora sênior de RH que atende pequenas empresas. Proposta: preparar a conversa de feedback a partir das anotações do gestor.

1. No Project da formação (espaço no Claude com instruções e arquivos fixos), abra uma conversa nova.
2. Anexe a ficha de problema, o resumo das conversas e a proposta com a métrica.
3. Peça: "Liste os papéis de usuário deste produto e o que cada um faz."
4. Resultado: gestor (registra anotações e prepara a conversa) e colaborador (lê o feedback final).
5. Peça: "Escreva 5 requisitos no formato 'Como [papel], quero [ação], para [resultado]'."
6. Peça: "Para cada requisito, escreva critérios de aceite no formato Dado / Quando / Então."
7. Confira um critério. Bom: "Dado um gestor com 3 anotações, quando pede o roteiro, então o roteiro cita as 3."
8. Reescreva os vagos. Ruim: "O roteiro deve ser útil."
9. Marque cada requisito: essencial para a proposta ou depois.

## Prática

1. Abra uma conversa nova no Project da formação.
2. Anexe `docs/ficha-problema.md`, `docs/resumo-conversas.md` e `docs/proposta-e-metrica.md`.
3. Peça os papéis de usuário e o que cada um faz.
4. Peça 5 a 8 requisitos no formato da Referência.
5. Peça critérios de aceite Dado / Quando / Então para cada requisito.
6. Aplique o teste do critério (Referência) e reescreva os vagos.
7. Marque cada requisito: essencial ou depois.
8. Salve em `docs/requisitos.md`.

## Checagem

Entrega: `docs/requisitos.md` com papéis, requisitos e critérios de aceite testáveis, marcados como essencial ou depois.

## Referência

**Formato do requisito**

- "Como [papel], quero [ação], para [resultado]."

**Formato do critério de aceite**

- Dado [situação inicial]
- Quando [ação do usuário]
- Então [resultado observável]

**Teste do critério**

- [ ] Duas pessoas diferentes chegariam ao mesmo veredito: passou ou não passou
- [ ] O resultado é observável na tela ou nos dados
- [ ] Sem palavras vagas: útil, rápido, fácil, intuitivo

**Exemplos**

| Requisito | Critério de aceite |
| --- | --- |
| Como gestor, quero registrar anotações sobre o colaborador, para não esquecer fatos | Dado um gestor logado, quando salva uma anotação, então ela aparece na lista do colaborador com a data |
| Como contador, quero conferir as notas do mês, para achar divergências | Dado um mês com 2 notas divergentes, quando roda a conferência, então as 2 aparecem marcadas |
| Como advogado, quero ver prazos da semana, para não perder nenhum | Dado um prazo em 3 dias, quando abre o painel, então o prazo aparece em destaque |

**Uso posterior**

- Requisitos e critérios: seção 4 do `SPEC.md` (especificação do produto, lição 1.6)
- Papéis: seção 2 do `SPEC.md`
- Requisitos "depois": `BACKLOG.md` (lição 1.7)
- Critérios viram testes automatizados: lição 2b.5 da T2

**Termos**

- Requisito: o que o produto deve permitir a um papel
- Critério de aceite: condição verificável que diz se o requisito está pronto
- Papel: tipo de usuário com permissões próprias (gestor, colaborador, admin)
