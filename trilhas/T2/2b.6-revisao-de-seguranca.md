# 2b.6 · Brechas encontradas e corrigidas antes de publicar (revisão de segurança)

- **Trilha:** T2 · Builder (T2b · MVP do projeto próprio)
- **Tempo:** 45 min
- **Evidência:** relatório + correções
- **Status:** rascunho, ainda não cursado pelo aluno zero

## Por quê

Um app no ar com chave exposta ou dados misturados entre usuários é um incidente, não um bug. Depois de publicado, o estrago é de outra pessoa.

A revisão de segurança procura essas brechas antes do deploy. O Claude Code revisa; você confere os itens inegociáveis um a um e decide o que corrigir agora.

Segredos fora do código e isolamento entre usuários são eliminatórios no marco da T2.

## Demonstração

Exemplo: revisão de segurança do Diário de Bordo antes de uma nova publicação.

1. Abra a pasta do Diário de Bordo no modo de código do Claude Desktop (ícone **</>**), em **Plano**.
2. Peça a revisão com o checklist (veja "Pedido de revisão", na Referência).
3. Leia o relatório: cada achado com local, risco e correção sugerida.
4. Confira o item mais grave por conta própria. Peça: "Mostre onde a chave do Supabase é lida e prove que não está escrita no código."
5. Confira o histórico. Peça: "Verifique se algum commit antigo contém segredo."
6. Classifique os achados: corrigir agora, corrigir antes do deploy, registrar no `BACKLOG.md`.
7. Troque para **Manual** e peça a primeira correção. Um commit por correção.
8. Rode todos os testes depois de cada correção.
9. Peça para salvar o relatório em `docs/revisao-seguranca.md`, com o status de cada achado, e faça o commit.

## Prática

1. Abra a pasta do seu projeto no modo de código, em **Plano**.
2. Peça a revisão com o checklist (veja "Pedido de revisão", na Referência).
3. Confira por conta própria os três itens eliminatórios: segredos, chamadas no servidor e isolamento.
4. Classifique cada achado (veja "Classificação", na Referência).
5. Troque para **Manual** e corrija os achados "agora" e "antes do deploy", um commit por correção.
6. Rode todos os testes depois de cada correção.
7. Salve o relatório em `docs/revisao-seguranca.md` com o status de cada achado.
8. Peça o commit e envie para o GitHub.

## Checagem

Entrega: `docs/revisao-seguranca.md` com achados e status + um commit por correção no GitHub.

## Referência

**Termos**

- Segredo: chave, senha ou token que dá acesso a um serviço
- Variável de ambiente: valor guardado fora do código; o código só lê o nome
- `.env.local`: arquivo local com os segredos (lição 2a.4)
- `.gitignore`: lista do que o git (guarda versões da pasta) não salva nem envia
- Servidor: parte do app que roda fora do navegador; o usuário não vê o que está ali
- RLS: regra no banco que limita quais linhas cada usuário vê e altera
- Histórico de commits: todas as versões salvas; um segredo num commit antigo continua exposto
- Deploy: publicar o app na internet (lição 2b.7)

**Pedido de revisão**

- "Faça uma revisão de segurança do projeto com este checklist. Para cada item: atende ou não, local, risco e correção sugerida. Não altere nada."

**Checklist de segurança**

- [ ] Nenhum segredo no código nem em commits antigos (eliminatório)
- [ ] Segredos só em variáveis de ambiente; `.env.local` no `.gitignore` e fora do GitHub (eliminatório)
- [ ] Toda chamada com chave roda no servidor (eliminatório)
- [ ] RLS ativa em todas as tabelas, com regra por dono (eliminatório)
- [ ] Usuário A não lê nem altera dados de B, nem trocando o endereço da página (eliminatório)
- [ ] Telas com dados exigem login
- [ ] Dados sensíveis da seção 5 do `SPEC.md` com tratamento aplicado

**Classificação**

| Classe | Quando | Ação |
| --- | --- | --- |
| Agora | Item eliminatório ou dado exposto | Corrigir nesta lição |
| Antes do deploy | Risco real, sem exposição atual | Corrigir antes da lição 2b.7 |
| Backlog | Melhoria sem risco imediato | Registrar no `BACKLOG.md` |

**Erros comuns**

- Segredo apagado do código mas presente em commit antigo: troque a chave no serviço; apagar não basta [VERIFICAR NA INTERFACE: onde gerar chave nova no Supabase]
- Confiar no relatório sem conferir: peça a prova de cada item eliminatório
- Corrigir tudo num commit: se algo quebrar, você não sabe qual correção causou
