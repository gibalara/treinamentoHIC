# 2b.2 · Regras que o Claude Code segue no seu projeto (`CLAUDE.md`)

- **Trilha:** T2 · Builder (T2b · MVP do projeto próprio)
- **Tempo:** 30 min
- **Evidência:** arquivo commitado
- **Status:** rascunho, ainda não cursado pelo aluno zero

## Por quê

O Claude Code começa cada conversa sem memória do projeto. O `CLAUDE.md` é o arquivo que ele lê sempre ao abrir a pasta.

Sem ele, você repete as regras a cada pedido e esquece alguma. A esquecida costuma ser a de segurança.

Você já tem um `CLAUDE.md` pronto: o do Diário de Bordo. Adaptar leva minutos; escrever do zero, uma tarde.

## Demonstração

Exemplo: as regras do Diário de Bordo revistas antes de servir de base a outro projeto.

1. Abra a pasta do Diário de Bordo no modo de código do Claude Desktop (ícone **</>**), em **Manual**.
2. Peça: "Liste as regras do `CLAUDE.md` em três grupos: gerais, específicas do Diário de Bordo e registros de erros resolvidos."
3. Confira o grupo **gerais**: segredos só em variáveis de ambiente, um commit por ciclo, protocolo de debugging.
4. Confira o grupo **específicas**: nomes de tabelas, telas e regras de negócio do Diário de Bordo.
5. Confira os **registros de erros**: cada um tem sintoma, causa, correção e como evitar (protocolo de debugging, lição 2a.6).
6. Peça: "Mostre, sem salvar, um `CLAUDE.md` só com as regras gerais e as seções do projeto vazias."
7. Leia o resultado e confirme que nada específico do Diário de Bordo ficou.

## Prática

1. Abra a pasta do seu projeto (`projeto-hic`) no modo de código, em **Manual**.
2. Peça para criar o `CLAUDE.md` a partir do da T2a (veja "Pedido de adaptação", na Referência). Sem T2a, use o "Modelo de `CLAUDE.md`", na Referência.
3. Peça para preencher a seção do projeto a partir do `SPEC.md`: problema, usuários, regras de negócio, fora do escopo.
4. Confira as regras de segurança uma a uma (veja "Regras inegociáveis", na Referência).
5. Peça: "Leia o `CLAUDE.md` e diga, em 5 tópicos, o que você vai e não vai fazer neste projeto."
6. Corrija o arquivo onde a resposta não bater com o que você quer.
7. Peça o commit com a mensagem "Adiciona CLAUDE.md do projeto" e o envio ao GitHub.

## Checagem

Entrega: `CLAUDE.md` commitado no repositório do projeto, com as regras inegociáveis e a seção do projeto preenchida.

## Referência

**Termos**

- `CLAUDE.md`: arquivo de regras que o Claude Code lê ao abrir a pasta (criado na lição 2a.2)
- Variável de ambiente: valor guardado fora do código, como senha ou chave; o código só lê o nome
- Segredo: chave, senha ou token que dá acesso a um serviço
- `.env` (ou `.env.local`): arquivo local com os segredos; nunca vai ao GitHub
- `.gitignore`: lista do que o git (guarda versões da pasta) não salva nem envia
- Servidor: parte do app que roda fora do navegador; o usuário não vê o que está ali
- Chave pública e chave secreta: a pública pode ir ao navegador, protegida pelo RLS; a secreta só no servidor
- RLS: regra no banco que limita quais linhas cada usuário vê e altera
- Protocolo de debugging: roteiro fixo para resolver erros (lição 2a.6)
- Commit: versão salva da pasta, ponto seguro para voltar

**Pedido de adaptação**

- Caminho da pasta: no Explorador de Arquivos, clique com o botão direito em `diario-de-bordo` > Copiar como caminho [VERIFICAR NA INTERFACE]
- "Leia o `CLAUDE.md` do Diário de Bordo em [caminho da pasta]. Crie o `CLAUDE.md` deste projeto: mantenha as regras gerais e descarte as do Diário de Bordo. Deixe a seção do projeto vazia."

**Regras inegociáveis**

- [ ] Segredos só em variáveis de ambiente, nunca no código nem nos commits
- [ ] Arquivos `.env` e `.env.local` no `.gitignore`
- [ ] Toda chamada com chave secreta roda no servidor; no navegador, só a chave pública
- [ ] Todo dado de usuário fica isolado: um usuário não vê o que é de outro
- [ ] Um commit por ciclo verificável, com mensagem curta no imperativo
- [ ] Erros seguem o protocolo de debugging e a solução é registrada aqui
- [ ] Sem feature de IA nesta versão (entra na T4)

**Modelo de `CLAUDE.md`**

```markdown
# [Nome do projeto]

## Projeto
- Problema:
- Usuários:
- Regras de negócio:
- Fora do escopo (ver BACKLOG.md):

## Pilha
- Banco e login: Supabase
- Publicação: Vercel
- Versões: GitHub

## Regras de segurança
- Segredos só em variáveis de ambiente. Nunca no código, nunca no GitHub.
- Arquivos .env e .env.local ficam no .gitignore.
- Toda chamada com chave secreta roda no servidor; no navegador, só a chave pública.
- Cada usuário só vê os próprios dados, garantido no banco.

## Forma de trabalhar
- Fonte de verdade: SPEC.md. Plano: PLANO.md.
- App básico antes de multiusuário.
- Um commit por ciclo verificável, mensagem curta no imperativo.
- Antes de alterar, mostrar o plano.
- Depois de gerar, explicar o arquivo do ponto de vista de arquitetura e risco.

## Erros resolvidos
- [data] Sintoma: ... | Causa: ... | Correção: ... | Como evitar: ...
```

**Protocolo de debugging**

1. Reproduzir o erro
2. Pedir hipóteses ao Claude Code
3. Testar uma hipótese por vez
4. Corrigir num commit só com a correção
5. Registrar em "Erros resolvidos" no `CLAUDE.md`
